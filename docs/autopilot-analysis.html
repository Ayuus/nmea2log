Autopilot course-keeping analysis

Prepared from the raw NMEA2000 log data (Actisense W2K-2), covering trips 1–13. Trip 14 was excluded (very short, engine only, autopilot never engaged).

Question

During trips 3 and 13 (and, as it turned out, every other trip too) the autopilot was observed weaving left-right-left-right around the intended course while steering a straight leg. The goal was to measure that weaving — its period and amplitude — from the logged data, as a starting point for tuning the autopilot to reduce it.

Method

Two NMEA2000 PGNs not currently decoded by the logbook app were decoded for this analysis:

  • PGN 127237 (Heading/Track Control) — the autopilot's own steering mode (Main Steering / Heading Control / Track Control / …) and its currently commanded course.
  • PGN 127250 (Vessel Heading) — the boat's actual compass heading. (PGN 127237 also defines a vessel-heading field of its own, but this autopilot never populates it, so 127250 was used instead.)

The first attempt compared GPS course-over-ground (COG) against a smoothed local average of itself, as a stand-in for "the intended course". That turned out to be a noisier, laggier proxy — COG reflects the boat's actual track over the ground, affected by current, leeway, wave action and GPS lag, not just the autopilot's own steering behaviour. The analysis below instead compares the boat's actual compass heading directly against the autopilot's own commanded course — literally the error signal the autopilot itself is trying to drive to zero — restricted to periods where the autopilot was confirmed to be actively holding a heading ("Heading Control" mode), split into continuous runs, with any dropout longer than 60 seconds starting a new run and runs shorter than 30 samples discarded as too short to measure reliably.

For each continuous run: the heading error (actual heading minus commanded course) was detrended against a short local average (to remove any slowly-drifting offset from current/leeway without hiding the oscillation itself), then period was measured as the time between successive zero-crossings of that detrended error, and amplitude as the peak absolute error within each half-cycle.

Aside: is "Navigation" mode visible in the data?

Alongside "Heading Control" (holding a fixed compass course), an autopilot/plotter combination can usually also be set to "Navigation" (follow a programmed route). PGN 127237 has a dedicated steering-mode value for this, "Track Control" — but across the entire logged history (not just these 13 trips), that value was never once seen. Only Main Steering, Heading Control, and Follow-Up Device appeared.

However, route/waypoint navigation data (PGN 129284, PGN 129283 — distance and bearing to the destination waypoint, cross-track error) was present hundreds of thousands of times, so route-following clearly was happening at times. Cross-referencing the two: whenever navigation data and "Heading Control" mode were both present at the same time, the autopilot's commanded course tracked the plotter's own computed bearing to the destination waypoint closely — a median difference of only 3.1° across 263,256 paired samples. In other words: this autopilot/plotter combination signals "Navigation" mode not through a distinct steering-mode value, but by the plotter continuously feeding the current route bearing into the same "Heading Control" commanded-course field a human would otherwise dial in by hand.

Caveats

  • This is exploratory analysis code, written directly against the raw log files for this question — it is not (yet) part of the shipped logbook app's own PGN decoding.
  • The 10% tail of larger course-tracking differences in the Navigation-mode check (p90 = 161°) is most likely waypoint-transition moments (bearing jumps to the next leg before the commanded course catches up) and/or periods where a route happened to be loaded but the autopilot was actually being steered manually — not evidence against the overall pattern.
